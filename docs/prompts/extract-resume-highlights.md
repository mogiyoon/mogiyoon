# 이력서 "개발 사항" 추출 프롬프트

특정 프로젝트 레포에서 이력서(포트폴리오 사이트)의 **경력 / 프로젝트 개발 사항** 항목을 뽑아내기 위한 재사용 프롬프트다.

## 사용법

1. 대상 프로젝트 디렉토리에서 Claude Code 를 실행한다 (포트폴리오 레포가 아니라 **분석 대상 프로젝트** 안에서 실행).
2. 아래 `---` 사이 블록을 통째로 복사해 붙여넣고, 상단 변수 4개만 채운다.
3. 산출된 JSON 을 포트폴리오 레포의 해당 파일에 병합한다.
   - `TYPE=project` → `public/data/resume-profile.json` + `public/data/resume-profile.en.json` 의 `projectHighlights`
   - `TYPE=work` → `public/locales/ko/introduction.json` + `public/locales/en/introduction.json` 의 `work.{WORK_ID}.projects.{PROJECT_ID}`

---

## 프롬프트 본문 (복사해서 사용)

```
# 역할

너는 시니어 엔지니어 겸 테크 리크루터다. 이 레포지토리를 조사해서, 이력서에 그대로 실을 수 있는
"개발 사항(Highlights)" 항목을 근거 기반으로 추출한다. 홍보 문구가 아니라 검증 가능한 사실만 쓴다.

# 입력 변수

- PROJECT_ID: <포트폴리오에서 쓸 프로젝트 id, 예: recho / pension>
- PROJECT_NAME: <사람이 읽는 프로젝트명>
- TYPE: <work | project>            # work = 회사 경력 프로젝트, project = 개인/사이드 프로젝트
- WORK_ID: <TYPE=work 일 때만, 예: deeptrade>
- MY_SCOPE: <내가 맡은 범위. 모르면 "조사해서 추론" 이라고 쓸 것>

# 1단계 — 조사 (반드시 먼저 수행)

다음을 실제로 읽고 근거를 수집한다. 추측 금지.

1. `README`, `docs/`, 설계 문서, ADR
2. `git log --author="$(git config user.email)" --no-merges --date=short --pretty='%h %ad %s'`
   — 커밋 메시지에서 반복되는 주제(성능, 테스트, 마이그레이션, 리팩터링, 인프라)를 군집화
3. 규모/영향이 큰 변경: `git log --no-merges --numstat` 상위 변경, 새로 생긴 디렉토리·모듈
4. 아키텍처의 비자명한 선택: 커스텀 훅/추상화, 네이티브 브릿지, 캐시 전략, 빌드 설정
   (`babel.config`, `metro.config`, `vite.config`, `webpack`, CI 워크플로)
5. 테스트/품질 자산: 테스트 파일 수, suite/test 개수(`jest --listTests` 등으로 확인 가능하면 확인), E2E 설정, lint/CI 게이트
6. 정량 지표의 근거: 벤치마크 스크립트, 성능 측정 로그, 번들 분석 결과, PR 본문, 이슈, CHANGELOG
7. TYPE=work 이면 AI/에이전트 활용 흔적도 조사: `.claude/`, `CLAUDE.md`, `agents/`, 스킬·하네스 정의, 프롬프트 문서

조사 결과는 내부적으로 "후보 항목 → 근거(파일 경로 / 커밋 해시 / 명령 출력)" 매핑으로 정리한다.

# 2단계 — 선별 기준

후보 중 다음을 만족하는 것만 남긴다. 목표 개수: 3~7개.

- 문제 → 해결 → 결과의 인과가 성립한다 (단순 "기능을 만들었다"는 제외)
- 기술적 판단이 들어갔다 (라이브러리 설치만 한 작업은 제외)
- 결과가 측정 가능하거나, 최소한 구조적 변화로 설명된다
- 내가 실제로 한 일이다 (MY_SCOPE 밖이면 제외하거나 "팀 작업 중 내 기여" 로 축소 서술)

우선순위: 성능·안정성 개선 > 자동화/테스트 체계 구축 > 구조 리팩터링 > 신규 기능 구현 > 도구·설정 개선

# 3단계 — 작성 규칙

- 어투: 공식적·기술적. 문장 종결은 "~함", "~됨", "~임" 으로 통일한다.
  블로그체·구어체·감탄 금지 ("빡세다" → "엄격함", "삽질" → "다수의 시도를 진행함").
- 수치는 **근거가 있을 때만** 쓴다. 근거가 없으면 수치를 지어내지 말고 정성적으로 쓴 뒤,
  마지막 `needsConfirmation` 목록에 "확인 필요: X 수치" 로 올린다.
- **증상과 메커니즘을 구분한다.** 관측된 사실(무엇이 일어났는가)과 원인 메커니즘(왜 그렇게 되었는가)은
  다른 종류의 주장이다. 메커니즘은 코드·스키마·문서에서 직접 확인한 경우에만 쓴다.
  "제약 조건이 없어서 → 중복 방지가 무력화되어 → N건이 누적됨" 같은 **그럴듯한 인과 체인을 추론으로 채우지 않는다.**
  이것이 이 프롬프트의 가장 흔한 오염 경로다. 증상만 확인됐으면 증상만 쓴다.
- **서로 다른 출처의 사실을 한 문장으로 합치지 않는다.** 각각은 참인데 결합이 거짓인 문장이 만들어진다.
  (예: 실제로는 "두 크롤러가 겹치는 종목 집합을 각자 수집" 인데, 별개로 본 테이블 정보와 엮여
  "한 테이블에 중복 키가 누적" 으로 왜곡되는 경우)
- 확인이 덜 된 문장은 **삭제하지 말고 본문에 `[확인필요]` 를 붙여 남긴다.** 조용히 매끄럽게 쓰는 것보다
  눈에 띄게 두는 편이 낫다. 사용자가 지우거나 확정하면 된다.
- 한 항목의 `title` 은 15자 내외의 명사구 (예: "API 분리 및 프리페칭 도입").
- 여러 동작을 나열할 때는 문장마다 개행(`\n`)으로 분리한다. 불릿 기호(-, •)는 넣지 않는다.
- 고유명사(라이브러리·도구명)는 정확한 표기를 쓴다.
- 영어판은 한국어 직역이 아니라 영어 이력서 관용 표현으로 재작성한다.
  과거형 능동태, 주어 생략, 측정치 우선 (예: "Cut main-screen load time from 2–3s to 0.6s by ...").

# 4단계 — 출력 스키마

TYPE=work 이면 스키마 A, TYPE=project 이면 스키마 B 로만 출력한다.
설명 문장 없이 JSON 블록 2개(ko / en) + 근거표 + 확인 필요 목록 순으로 출력한다.

## 스키마 A (TYPE=work) — locales/{ko,en}/introduction.json 의 work.{WORK_ID}.projects.{PROJECT_ID}

{
  "name": "프로젝트명 (기술 스택 표기 가능)",
  "position": "담당 포지션",
  "period": "YYYY.MM ~ YYYY.MM",
  "highlights": [
    {
      "title": "항목 제목",
      "problem": "어떤 문제/제약이 있었는지. 배경과 영향 범위를 포함함.",
      "analysis": "(선택) 원인 분석 과정. 없으면 키 자체를 생략함.",
      "solution": "무엇을 어떻게 했는지.\n동작 단위로 개행 분리함.",
      "result": "결과. 가능하면 before → after 수치로 표기함."
    }
  ],
  "aiHighlights": [
    {
      "title": "AI 활용 항목 제목",
      "summary": "한두 문장 요약. 이력서 본문에 단독으로 실릴 수 있는 밀도로 작성함.",
      "context": "왜 필요했는지. 도입 전 상황과 관찰된 문제.",
      "approach": "어떤 구조로 설계·운영했는지. 단계별로 개행 분리함.",
      "verification": "결과를 어떻게 검증했는지. 사람이 폐기·수정한 부분도 함께 기술함.",
      "impact": "정량 지표 + 정성 변화. 유의미하지 않은 지표는 그렇게 적음."
    }
  ]
}

- `highlights` 는 이력서에 기본 선택되는 항목이다. 가장 강한 것부터 정렬한다.
- `aiHighlights` 는 기본 미선택 항목이다. AI/에이전트 활용 근거가 없으면 빈 배열로 둔다.
- `impact` 에는 과장 금지. 개선이 확인되지 않은 지표는 "유의미한 감소는 확인되지 않음" 처럼 그대로 적는다.

## 스키마 B (TYPE=project) — data/resume-profile{,.en}.json 의 projectHighlights.{PROJECT_ID}

{
  "teamType": "개인 프로젝트 | 팀 프로젝트",
  "summary": "이 프로젝트가 무엇인지 한 문장. 사용자 관점의 가치로 서술함.",
  "highlights": [
    {
      "title": "항목 제목",
      "body": "문제 상황 → 시도/판단 → 구현 → 결과·배운 점을 3~5문장으로 이어 씀. 문단 하나로 작성함."
    }
  ]
}

- `highlights` 는 2~3개로 압축한다 (개인 프로젝트는 밀도가 중요함).
- `body` 는 개행 없이 한 문단. 마지막 문장에 얻은 역량/이해를 한 줄 넣는다.
- en 파일의 `teamType` 은 "Personal Project" / "Team Project" 로 쓴다.

# 5단계 — 근거표와 확인 요청 (JSON 뒤에 이어서 출력)

| 항목 title | 문장/수치 | 근거 | 근거 종류 |
|---|---|---|---|
| ... | "N건 누적" | `src/x/y.ts:120`, 커밋 `a1b2c3d`, 실행한 명령과 그 출력 | 코드 / 커밋 / 문서 / 측정 |

- **본문에 등장한 모든 수치를 한 행씩** 적는다. 근거 칸을 채울 수 없는 수치는 본문에서도 지운다.
- 원인 메커니즘을 서술한 문장도 한 행씩 적고, 어디서 그 메커니즘을 확인했는지 밝힌다.

확인 필요 (needsConfirmation):
- 수치나 사실 중 레포에서 확정할 수 없어 사용자 확인이 필요한 항목을 목록으로 제시함.
- 각 항목에 "이렇게 쓰려면 무엇을 알려달라" 를 함께 적음.

# 금지 사항

- 레포에서 확인되지 않은 수치·기술·성과를 만들어내지 않는다.
- 확인된 증상에 그럴듯한 원인을 붙여 완결된 서사로 만들지 않는다. 불완전한 사실이 매끄러운 허구보다 낫다.
- 다른 사람이 한 작업을 내 성과로 쓰지 않는다. 불확실하면 확인 요청으로 돌린다.
- "~를 담당했습니다", "~를 통해 성장했습니다" 같은 자기소개서 문장을 쓰지 않는다.
- JSON 밖에 마케팅성 수식어를 덧붙이지 않는다.
```

## 병합 시 체크리스트

- [ ] ko / en 두 파일의 항목 개수와 순서가 일치하는가
- [ ] `TYPE=project` 인 경우 `resume-profile.json` 의 `projectOrder` 에 id 를 넣을지 결정했는가
- [ ] `TYPE=work` 인 경우 `public/data/introduction.json` 의 `workExperience[].projects[]` 에 `{ id, tech }` 가 등록돼 있는가
- [ ] 어투가 "~함 / ~됨 / ~임" 으로 통일돼 있는가
- [ ] 수치가 실제 근거와 일치하는가 (근거표 확인)
